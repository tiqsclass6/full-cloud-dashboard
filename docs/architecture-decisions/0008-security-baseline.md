# **ADR 0008: Security baseline (Phase 7)**

- Status: accepted
- Date: 2026-10-30

## **Context**
Phases 1-6 built a working platform with little defence in depth: Kafka accepted plaintext connections from anyone in the cluster, every namespace could reach every other, most pods ran as root, nothing checked what was deployed, Argo CD could deploy anything anywhere, and the AWS environment's secrets were copied in by a script. The target role is federal-facing, so the controls also need to be traceable to a recognised framework (NIST SP 800-53).

## **Decisions**
1. **Kafka: mutual TLS and ACLs, no plaintext listener.** Each client is a Strimzi `KafkaUser` with its own certificate and least-privilege ACLs: the ingestion service may write `events.raw`; the Flink job may read it with its own consumer group. A `kafka-admin` super user exists only for the admin toolbox the scripts use. Strimzi's listener NetworkPolicy admits only the client namespace and the toolbox.
2. **Kyverno distributes the client certificates.** Strimzi writes certificates into the `kafka` namespace; clients run in `apps`. A `GeneratingPolicy` copies the labelled secrets and keeps the copies in sync, so certificate renewals reach the clients without a script. This requires giving Kyverno cluster-wide read and write access to Secrets, a concentration of privilege accepted because Kyverno is part of the control plane.
3. **Kyverno's CEL policy types, not `ClusterPolicy`.** Kyverno 1.19 deprecates `ClusterPolicy`; a new project starts on `ValidatingPolicy`, `GeneratingPolicy` and `ImageValidatingPolicy`.
4. **Enforce in our namespaces, audit everywhere else.** Pod Security admission enforces `restricted` in `apps`, `data` and `kafka`, and audits and warns elsewhere. Kyverno rules (requests and limits, pinned images, approved registries, ClusterIP-only Services) deny in the platform namespaces and report elsewhere. New rules are rolled out in Audit first and switched to Enforce after the reports are clean. Locally `data` enforces `baseline`, because the stand-ins for managed services (Postgres, SeaweedFS) start as root; they do not exist on AWS.
5. **Default-deny network policies with explicit flows.** Each platform namespace denies all ingress and egress, then allows DNS, same-namespace traffic, Prometheus scrapes, HTTPS egress where needed (never to the instance metadata address) and a short list of cross-namespace flows. On EKS the VPC CNI's network policy agent enforces them (`enableNetworkPolicy`); without it EKS accepts policies and ignores them.
6. **Least-privilege Argo CD projects.** Operators (which need CRDs, cluster roles and webhooks) are separated from the platform's own charts, which may create only the namespaced kinds they use, plus the platform namespaces and Kyverno policies. The `default` project is emptied, so an application without a proper project fails instead of running with unlimited rights.
7. **Secrets from AWS Secrets Manager through External Secrets.** RDS generates and rotates its own password; Terraform writes Grafana's with a write-only argument from an ephemeral value. Neither appears in Terraform state, Git or a script.
8. **Supply chain: scan, inventory, sign, verify.** Trivy gates on HIGH or CRITICAL vulnerabilities that have a fix and sit in a layer we control, and on IaC misconfigurations. Fixable OS-package findings are gated too, so images whose base lags behind apply the distribution's security updates at build time; unfixed base-image findings are reported, not gated. Findings in libraries that third-party jars shade, and fixes not yet 14 days old, are accepted explicitly, each with a reason and an expiry date, in `.trivyignore.yaml`. Every image gets a CycloneDX SBOM. On AWS, images are signed by digest with a KMS key (Cosign; the key never leaves KMS), and Kyverno refuses unsigned images from the platform's ECR repositories.
9. **Account-level audit outside the environment.** CloudTrail (multi-region, validated, KMS-encrypted, one-year retention), IAM Access Analyzer and GuardDuty alerts live in the bootstrap stack. The account's existing GuardDuty detector and Security Hub are left as they are. AWS Config records only the platform's resource types, and only while an environment exists, because the account's Security Hub standards bring several hundred Config rules whose evaluation cost would otherwise apply to everything.

## **Consequences**
- Every control has an automated test: `make security-test` (Kafka, network and admission policies) and `make security-scan` locally, `make aws-security-test` on EKS. The mapping to NIST SP 800-53 is in [**docs/security/control-mapping.md**](../security/control-mapping.md).
- A sync that fails for a policy or project reason keeps retrying the old revision; it has to be terminated before Argo CD picks up the fix (seen once while rolling this out).
- In-cluster HTTP between services (ingestion service, schema registry, Iceberg REST catalog) is not encrypted. Network policies restrict who can connect, but encryption in transit inside the cluster needs a service mesh or per-service TLS, which is not in this phase.
- Image signatures are verified on AWS only; locally images are loaded straight into kind with no registry to verify against.
